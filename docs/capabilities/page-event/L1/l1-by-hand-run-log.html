Inputs and outcome

  • One read-only pull of GET /api/admin/agent-domains-mine/admissions/admissions-signals, with the limits the platform team approved (35 visitors, 20 events per visitor).
  • For each of the first 10 visitors with page events: up to 20 most recent page events (path, title, time) and the interest tags already saved.

Where the outcome was recorded. The outcome is interest tags for each visitor. The builder has read access only, so, as the portal assistant (Cory) advised, the tags are recorded in this run log and nothing was written to the platform.

Steps actually performed

  1. Read the platform code to learn the real tagging rules (admissionsVisitorActivityAgent.ts:65-68).
  2. Pulled once in the Command Center's Visitor sample tab.
  3. For each visitor, read every page path, checked each against the 4 rules, and chose the tag(s).
  4. Wrote a reason for each tag and noted anything surprising.
  5. Compared each tag with the tags the system had already saved.
  6. Downloaded the tags, reasons and timer (run-log-entries.json, kept locally, not committed).

Judgment calls

  • Pages that match no rule (home, services, platform, how it works, blog, proof, book, demo pilot, portal pages): left untagged. A visitor is "unclassified" when nothing matched, instead of guessing.
  • Mixed visitors (V03, V04, V06, V07): tagged only the pages that matched, and named the unmatched pages in the reason.
  • Partial history: for 8 of 10 visitors only the latest 20 events were visible. The tag was decided from what could be seen, and this was noted.

Where the recorded workflow differed from the real work

From doing it by hand:

1Every page title was emptySo decisions could only be made from page paths.
2Repeated eventsThe same page was often recorded 2–6 times in the same minute. These look like duplicates, but not always: V06 had one page once and another 3 times.
3Only part of the history8 of 10 visitors were partial, down to 20 of 13,100 events (V09). This explains most of the 4 differences from the saved tags.
4Existing users, not applicants4 of 10 (V02, V06, V09, V10) used portal pages such as login. The brief assumes "a prospective applicant".
5The most interested visitor gets no tagV05 moved from home to services, how it works, platform, demo pilot and book in 3 minutes. No rule covers demo or booking pages.
6Patterns over time are invisibleV07 came back over a month; V01 and V08 viewed one page about once a minute. A person notices these; the rules see only single pages.
7Saved tags mix sourcesV09 has "outcomes" and "strategy_call", which page rules can't produce; they come from chats. Nothing records which source added which tag.
8No programme could be identifiedThe brief talks about "programme affinity", but only 4 general tags exist.

Mechanical vs judgment

Mechanical (a tool could do it)

  • Checking each path against the 4 rules
  • Merging tags
  • Counting

Needs judgment (a person, or a better rule set)

  • Pages that show interest but match no rule (demo, booking, platform)
  • Recognising existing users
  • Patterns over time
  • Deciding when 20 events aren't enough
